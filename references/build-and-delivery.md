# 编译、保留附录与交付

保存原文件及哈希，确认正文计数和附录开始页。用户指定文件是内容基线，源只是编辑工具。主文件处理通用样式、逐问文件处理内容，记录实际编译入口及工具版本，不覆盖项目模板配置。

编译后检查缺字、未定义引用、错误、overfull 等。扫描 PDF 的 `\frac`、`\partial`、`$` 等痕迹后人工确认：正文可能讨论 LaTeX，存在误报；抽取顺序也可能不可靠。附录代码不纳入正文公式扫描。

国赛 CUMCM 匿名论文首页应直接呈现论文标题与摘要，不添加题号、队号抬头。项目配置中的赛题号和队号仍可保留供非匿名页面使用；若本地论文源另写了这些字段，只删除匿名正文里的输出语句。用 `pdf_workflow.py audit body.pdf --cumcm-anonymous --project-config .mathmodel/paper/config.json --report qa/anonymous.json` 检查首页字段和所选正文中的队号原值；检查报告只写问题类别，不写队号。PDF 文本提取不能保证识别扫描图或转曲文字，仍须查看首页渲染图。

## 原附录接回

正文单独编译，插入用户原 PDF 的附录页，不将整页栅格化重建。`pdf_workflow.py append` 默认不修改原页码。授权补页码时使用 `--number-pages`，脚本会：

1. 拒绝覆盖输入或已存在的输出，拒绝旋转页（需另行处理并核验）。
2. 检查页脚带有无文字或非白像素，包括扫描图内的旧页码、线条；非空则停止，不白块覆盖。
3. 写页码后逐页比较原附录的渲染与文字；无页码时比较整页，有页码时比较页脚上方并核对页码。
4. 验证成功后写正式输出与输入/输出哈希报告。

这是页面视觉与文字保真，**不保证 PDF 字节相同，也不保证数字签名有效性、全部书签、表单及文档级元数据**。此类需求需专门流程。

边距参数顺序上、右、下、左；页号从 1 起，末页包含。页脚高度与基线距离从页面底部计，单位 pt，不能假定版心外必定空白。

## 支撑包

用户/比赛决定内容。通常包括逐问入口、共用模块、验证与绘图脚本、环境说明、处理后的题目附件、结果文件、AI 使用说明。赛题正文与处理后的数据附件是不同类别；是否收录各自由要求决定。

显式白名单避免整个项目递归入包。`package_support.py` 接受：

```json
[
  {"path": "code/problem1.py", "description": "问题一独立求解入口"},
  {"path": "data/processed.csv", "description": "清洗后的观测数据"},
  {"path": "results/result1.xlsx", "description": "问题一结果"}
]
```

脚本检查路径在根目录内，无符号链接越界、重复和大小写冲突，拒绝常见缓存、凭据及环境文件。它不能判断 CSV 内的个人信息，公开前仍需检查内容。生成 `MANIFEST.json`，含相对路径、说明、大小和 SHA-256，并回读 ZIP 验证。显示四位小数的表格仍须配套未舍入计算及判定记录。

## 产物发布与回读

求解前发现当前宿主的真实输出范围：程序工作目录、允许写入/登记的路径、发布扫描范围、文件列表、下载及归档方式。`results/` 不是所有使用者的固定目录；既有项目也可能使用 `result/`、`results_full/` 或 `code/outputs/`。对照每问实际入口和导出路径，登记全部必需电子表、未舍入字段、终点记录及图源。优先沿用用户项目；只修本次新产物的登记或明确的路径映射，不因目录名称改变原件、旧论文或历史结果。

分开记录三个状态：

1. **生成候选**：执行快照/临时目录中真实存在文件，记录入口、源码与输入版本、退出状态及候选字节/哈希。失败或超时也可能留下部分文件，存在不代表内容合格。
2. **发布到当前项目**：宿主允许的目录中保存同版文件，其文件列表实际返回该路径。某次 `published=true` 可能只发布了报告，不能据此称同次所有工作簿或原精度字段已发布。
3. **使用者可取得**：实际下载副本或最终 ZIP 成员回读后，路径、大小和哈希与经审查产物一致。链接、文件清单或打包指令只说明意图，不能代替取回字节。

当前列表缺必需结果时，先查该次执行的真实候选与宿主扫描范围，分别记录“未生成”“生成但未登记/发布”“发布但取回版本不符”。仅在候选快照存在的文件不称已交付；也不能因为工具未扫描该目录就断言求解器没生成。候选恢复/复制属于一次新的明确操作，须保留来源与内容核验、选择新的允许目标，不能自动覆盖已接受成品。

可选 [`check_artifact_handoff.py`](../scripts/check_artifact_handoff.py) 只读核对声明的产物哈希、当前文件、**实际捕获的**宿主列表与下载/ZIP字节。例如合同由代理按真实产物填写：

```json
{"schema_version":1,"artifacts":[
  {"path":"result/result1.xlsx","sha256":"替换为真实小写SHA-256"},
  {"path":"results_full/q1_full.npz","sha256":"替换为真实小写SHA-256"}
]}
```

```sh
python scripts/check_artifact_handoff.py reports/artifact-handoff.json --project-root . --listing reports/host-list.json --candidate-root /path/to/execution-snapshot --archive support.zip
```

`--candidate-root` 可省略；实际下载采用 `--download-root`，同时声明下载和ZIP时两者都须同版。`--listing` 接受宿主返回的 `{"files":[{"path":"...","sha256":"..."}]}`（哈希字段可不存在），不能由模型编造列表证明发布。存在明确命名映射时，各项可列 `candidate_path`、`archive_path` 或 `download_path`；映射不自动移动文件。退出0仅表示本次声明产物的交接证据吻合，1表示缺失/过期/未完成回读，2表示合同或输入不合法。工具不执行、登记、发布、恢复或认证科学正确；普通宿主可以用等价回读完成同一核对，不必使用此脚本或先要求用户编写合同。

## 按本次范围检查交付清单

从零全交付或多个文件一起交付时，把[清单示例](../examples/project-delivery.json)改成该项目的 `reports/project-delivery.json`。从题面逐项填写全部子问和要求的电子结果，清单只是用户已选范围的记录。简单改标题或一张图时不用新建完整清单。

- `mode` 对应六项方向：`revise`、`write-from-results`、`full-delivery`、`review-only`、`diagram-only`、`layout-only`。
- `deliverables` 只列实际约定的文件，`required=true` 才是本次必需；未要求 Word 时可删去或标为可选，不因示例存在便强制交付。代码、图源、环境说明、AI材料、检查报告可按要求加入。
- `questions` 记录每问独立入口、真实运行命令和原精度结果路径。`full-delivery` 必须填写；其他路线只在确实要核对求解材料时填写。对照题面确认数量，脚本无法知道你有没有漏抄某一问。
- 用户要求保留原文件时，在 `preserved_inputs` 列出项目相对路径和接手时的真实 `sha256`；没有原附录的新论文可留空。原 PDF 附录页面保真仍由 `append` 检查，文件哈希不能替代页面比较。

```sh
python scripts/check_project_delivery.py reports/project-delivery.json --project-root . --report qa/round-01/inventory.json
```

脚本只读扫描声明文件，检查必需文件缺失、空文件、重复输出、逐问代码/结果和保留源哈希。报告含相对路径、大小、SHA-256，使用新的报告路径，不覆写原文件。清单中的运行命令仅被记录，**不会由此脚本执行或输出原文**。退出码 0 表示文件清单完整，1 表示有缺失/变化，2 表示清单或路径不合法。

`inventory_complete=true` 仅说明清单中的文件存在且非空，文件内容、模型正确性、PDF/Word格式和论文论证仍按专项检查核验；不能凭空白但非零长度的文件或任意占位内容宣称“全套完成”。从零新稿无须构造“旧附录”以调用 `verify_delivery.py`；有原附录拼接时再用后者做同版本比对，有支撑包时单独做 ZIP/白名单回读。

## 验收

看正文全篇联系页与重点页原尺寸：摘要、方程组、双表、联图、问题交界、文献、附录衔接。核对编号、引文、页码、字形、遮挡、孤行和图表顺序。只报告实测指标。公开 skill 时仅发布通用流程、原创说明及代码，不混入论文、赛题、附件、个人路径或团队档案。

完成独立 PDF 审核、附录拼接与支撑 ZIP 后，运行 `verify_delivery.py` 做同版本核对：正文哈希须同时匹配 PDF 审核报告和附录拼接报告，原附录与最终 PDF 哈希须匹配拼接报告；正文审查应覆盖整个正文 PDF，页数与附录验证数须一致。提供支撑 ZIP 时，逐文件核对 ZIP 清单、内容哈希和大小；若传入 `--support-root`，还与当前源文件比较。任一文件在出报告后被修改就不应交付，先重做相应步骤再检查。

```sh
python scripts/verify_delivery.py body.pdf original.pdf final.pdf qa/layout.json qa/appendix.json --support-zip support.zip --support-root support-root --report qa/delivery.json
```

此门禁不检查模型结论、引用真实性、图文遮挡或 Word 分页，仍须按前文单独核验。
