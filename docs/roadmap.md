# 开发与优化方向

制定日期：2026-10-01。基线提交：`82f4481`。本页是后续开发计划；只有[核验记录](validation.md)及对应代码、运行产物能证明已经实现的能力。

## 目标与当前基础

围绕一个目标推进：**从使用者选择的任务范围出发，让每个需要交付的结果都能按题意、来源和实际验证情况验收。** 优先补证据和检查能力，再改交互与便利性。每一轮保持现有六种工作方向和用户已经选定的模板、工具、附录保留约定。

| 当前已具备 | 当前边界 | 对应位置 |
| --- | --- | --- |
| 六项任务方向、逐步问询、模板盘点与决策记录 | 大部分题意、交付范围仍由代理手工整理 | [模板选择](../references/template-selection.md)、`template_inventory.py` |
| 交付文件及逐问代码/结果清单 | 验证存在、非空、哈希；不能判断一个扩展名为 PDF 的文件是否真能打开 | [清单检查](../scripts/check_project_delivery.py) |
| PDF 页数、连续空白、原公式文本与匿名抬头检查 | 不自动证明公式正确或图文不重叠；正文数值尚未自动关联到结果源 | [PDF 工具](../scripts/pdf_workflow.py) |
| 原附录保真、白名单支撑包与同版本核对 | 模型含义、引用真实性、Word 分页要另外审查 | `verify_delivery.py`、`package_support.py` |
| 官方工具指南、固定上游子模块、Windows/Ubuntu 脚本测试 | 安装说明不能代替本机环境探测；脚本测试不能代替代理行为评测 | [工具指南](toolchain.md)、[核验记录](validation.md) |

## 优先级与验收标准

### P0：交付内容真实、题意覆盖完整

| 开发项 | 要解决的具体问题 | 实现方向 | 完成标准 |
| --- | --- | --- | --- |
| P0-1 文件格式与结果表检查 | 非空占位文件可能通过清单；表格存在却缺工作表或后半段数据 | 在清单工具中增加可选的类型检查；PDF、DOCX、XLSX、ZIP 分别验证结构；电子表按用户声明的表名、列、时间范围、步长和域外规则核对 | 损坏/伪扩展名文件被识别；缺表、缺列、采样断档和错误终点的夹具失败；合法且未要求的可选格式不阻挡交付；大表以流式方式检查 |
| P0-2 题意与任务合同 | 文件清单只知道填入的 Q1，无法发现题面实际还有 Q2 | 将全部子问、正文展示要求、电子文件要求和验收项整理为有来源位置的任务合同，再与交付清单比较 | 已知子问遗漏、正文和电子范围混淆会报告；缺少或含糊条件标为待明确；用户新指示有来源与版本，旧值不会覆盖新值 |
| P0-3 数字与来源关联 | 摘要、图表和结果文件可能用了不同版本或不同舍入值 | 为关键结果建立数值标识、源文件哈希、JSON字段/表格位置、单位、展示精度与容差；按这些标识检查论文源、表和图的引用 | 更改结果源后相关论文结论标为需复验；超出容差、单位含义冲突被报告；计算精度与显示精度分别保留；不对全文所有数字盲目匹配 |

这三项按 P0-1 → P0-2 → P0-3 推进。先建立可信的文件与任务接口，避免后面的比较器拿错对象。

### P1：可重复运行、定位论文问题

| 开发项 | 实现方向 | 完成标准 |
| --- | --- | --- |
| P1-1 逐问复现记录 | 在实际运行后统一保存解释器/软件版本、参数、输入哈希、退出码、日志及输出哈希；运行器只执行本次明确选择的结构化命令，在独立输出目录运行 | 相同输入能重跑；失败或超时保留日志；旧输出不会冒充新结果；不同软件对照与实测验证采用不同证据类别。当前清单中的文本命令继续保持只读，不被直接当 shell 执行 |
| P1-2 公式、图表与分页诊断 | 在已有 PDF 检查上加入越界、裁切及图文关系的候选问题定位；保留逐问公式、图源标签和引用锚点；为 Word 单独建立渲染检查记录 | 报告能指出页号、区域和对应源；发现问题后重渲染；自动候选与人工确认分开记录；PDF 通过不推出 DOCX 通过；不把低留白当作图文无重叠 |
| P1-3 文献证据记录 | 保存题名、作者、出处、访问来源、核验时间和与正文主张的对应；分别记录期刊条目核验与 CNKI 收录核验 | 不存在的条目、悬空引用、编号不一致能定位；要求知网可查而证据不足时列为待核验；网络不可用时保留状态，不能自动标为通过 |

P1 的目标是把修订意见落实到位置和证据。修复后的验收仍使用同一轮源文件、结果、PDF/Word和报告。

### P2：使用体验与持续维护

| 开发项 | 实现方向 | 完成标准 |
| --- | --- | --- |
| P2-1 环境检查与接续任务 | 优先复用已集成的环境检查入口；按当前路线只读检测解释器、依赖与编译器；记录阶段输入/输出哈希以判断哪些步骤需重做 | 同一环境安装与执行一致；只修 PDF 不要求安装商业软件；恢复后从最近有证据的阶段继续；结果变化只使相关下游阶段失效 |
| P2-2 真实行为回归 | 为六种方向准备匿名合成请求与原始材料，记录实际问询、选择、动作、文件和判定；继续维护脚本测试 | 能发现反复询问、模板越权切换、只交 PDF 却声称全交付、把未执行验证写成已通过等行为；未实际运行的情景不会计入通过数量 |
| P2-3 上游兼容性维护 | 按用户已明确的半月检查偏好接续维护，实际频率以任务配置为准；对入口、模板、接口和许可变化分项审查，按受影响路线运行回归 | 更新后必需入口可用、原有项目配置未被覆盖；失败保留旧固定版本；版本更新通知说明实际变化和验证结果 |

## 建议的首个开发包

下一步先做 **P0-1 文件格式与结果表检查**，范围限定为：

1. 为交付清单增加可选 `kind` 与格式检查结果；旧清单仍能运行。
2. PDF 检查能打开且有页面；DOCX 检查 ZIP 和核心文档结构；XLSX 检查工作簿/工作表结构；支撑 ZIP 复用现有清单与内容哈希校验。
3. 先支持电子表最常见的表名、列名、首末时刻、行数和固定采样间隔检查，复杂空间域规则通过明确的扩展检查器处理。
4. 增加“假PDF、坏DOCX、少工作表、缺时间段、可选Word未要求”正反例；先在合成目录测试，再对获授权的真实项目副本复核。
5. 报告分别显示文件完整性、结构有效性和任务范围检查结果；任一项的“通过”只覆盖它实际检查的内容。

这一步完成并验收后，再推进任务合同与数值来源关联。开发包按可独立审查的变更合并，不一次重写全部现有工具。

## 发布与衡量

- 每个开发包先写输入、输出、兼容方式和失败情景，再实现；验证新能力后更新 README、示例和实际核验记录。
- 继续运行 Windows/Ubuntu 回归；GUI 渲染、文献来源、模型含义和代理行为测试单独给出实际执行记录。
- 用漏项、误报、旧报告错配、重复询问和复现失败等实际案例衡量改进；新增文档页数、工具数量和测试数量不单独作为完成指标。
- 一篇论文的页数、边距、留白阈值和软件路线仍是项目约束，不扩展为全部比赛的统一标准。
